# 1 绪论

## 1.1 项目背景及意义

### 1.1.1 项目背景
当前智能家居正朝着 “智能化、场景化、健康化” 方向发展，但传统家居系统存在功能单一（多仅覆盖安防或环境监测）、交互不便（依赖按键 / APP）、数据孤岛（设备间联动弱）、健康维度缺失等问题；同时边缘计算与 AI 视觉技术的成熟，为家居场景下的 “本地智能 + 云端协同” 提供了技术基础，用户对 “安全防护 + 健康管理 + 便捷控制” 一体化家居系统的需求日益提升。

### 1.1.2 项目意义
1. **功能融合，提升家居体验：** 整合环境感知、健康采集、智能控制等功能，多控制方式（手势 / APP / 手动），解决传统家居系统功能割裂的痛点，让家居管理更便捷。
2. **技术落地，推动边缘智能普及：** 基于 X-CUBE-AI 实现 AI 手势识别的边缘端部署（INT8 量化加速），结合多传感器融合技术，降低 AI 与物联网技术在家庭场景的应用门槛，为边缘智能家居提供可参考的技术方案。
3. **安全健康双守护，强化居家保障：** 实现心率血氧、环境参数的实时监测与异常告警，填补了传统家居系统 “健康管理” 的空白，提升居家安全性与健康关怀。
4. **云端协同，实现智能化管理：** 借助OneNET云平台完成数据存储、远程监控与消息推送，结合本地 Flash 存储配置，兼顾 “本地实时响应” 与 “云端全局管理”，提升系统的可靠性与扩展性。

## 1.2 国内外研究现状
当前国内外智能家居安防与健康系统的研究，均聚焦 “边缘智能 + 多维度融合 + 云边协同” 的技术方向，但存在差异化特点：
1. **国外：** 技术更侧重无感化监测、轻量化 AI 的成熟落地，在非接触式健康检测（如无线信号生命体征监测）、边缘 AI 模型的商业化应用（如谷歌、亚马逊的终端手势 / 行为识别）上领先，但本土化场景适配不足。
2. **国内：** 更聚焦功能整合与低成本工程化，通过物联网平台实现设备规模化接入，同时探索多模态安防（如本项目的 “指纹 + 超声 + 视觉”）、本地化通信（蓝牙近场配网）等场景创新，但在无感化健康技术、AI 模型自主轻量化能力上仍有短板。

整体来看，行业正从 “单一设备智能” 向 “系统级安全健康守护” 升级，而本项目的 “多传感器融合检测与报警 + 边缘 AI 手势控制 + 健康数据本地 - 云端同步”，是对当前国内外技术方向的综合落地与局部创新。
### 1.2.1 国内研究现状
1. **安防与健康的系统集成**
   国内更侧重**本土化场景的功能整合**：小米、华为等企业推出 “智能门锁 + 摄像头 + 健康传感器” 套装，支持指纹 / 人脸双认证 + 心率血氧监测，但健康数据多依赖云端处理；本项目采用的 “指纹 + 超声 + AI 视觉” 多模态安防方案，在误报率优化（入侵置信度评分）上属于国内前沿探索。
2. **边缘计算与 AI 推理落地**
   AI 边缘推理技术快速普及：依托 STM32、ESP32 等低成本芯片，国内开发者通过 X-CUBE-AI 等工具实现 PyTorch 模型的终端部署，支持手势识别、异常行为检测等功能；但在模型轻量化（如 INT8 量化加速）的工程化应用上，与国外仍存在一定差距。
3. **物联网平台与本地化通信**
   OneNET、华为云 IoT 等平台已实现**MQTT 协议的大规模设备接入**，支持传感器数据上报、远程控制；同时，国内企业探索 “蓝牙近场通信 + 本地 Flash 存储” 方案（如本项目的配网 / 控制功能），解决网络中断时的设备离线可控问题。

### 1.2.2 国外研究现状
1. **智能家居安防与健康融合**
   国外聚焦**无感化健康监测 + 主动安防**的技术突破：例如 MIT 开发的 Vital-Radio 技术，通过无线信号实现非接触式心率、呼吸监测，精度达 99%，已应用于老人居家监护场景；谷歌 Nest 系列则整合 AI 视觉与环境传感器，实现 “行为异常检测 + 环境参数联动”，支持火灾、入侵的多维度预警。
2. **AI 边缘计算与交互技术**
   头部企业推动**轻量化 AI 模型的边缘部署**：苹果 HomeKit、谷歌 Home 支持基于终端设备的手势识别（如隔空操控智能家电），采用 INT8 量化等技术降低算力需求；同时，亚马逊 Ring 系列通过 “云端训练 - 边缘推理” 架构，实现本地端的人体姿态识别与实时告警。
3. **多传感器融合与云端协同**
   多传感器融合技术成熟度较高：例如博世、英飞凌的毫米波雷达 + 视觉传感器方案，可穿透障碍物实现人体生命体征监测；云端层面，亚马逊 AWS IoT、谷歌 Cloud IoT 采用 MQTT 协议构建 “设备 - 边缘 - 云端” 三级架构，支持海量设备的低延迟通信与数据同步。

# 2 系统设计方案

## 2.1 系统概述
此系统旨在实现智能家居环境下的智能家居控制与健康守护功能，结合摄像头模块与AI边缘计算技术，实现手势识别控制。系统通过WiFi模块将传感器数据与安防状态上传至云平台进行处理和存储，同时支持蓝牙模块实现近场低延迟通信与手机APP控制。系统集成了环境参数监测、健康数据采集、智能设备控制与异常报警等功能，支持手势交互、远程监控及多传感器融合安防。
系统主要由AI视觉模块、多传感器采集模块、通信模块、用户交互模块和云端管理平台组成。通过云平台，用户可以远程查看家居环境数据及健康信息，可通过蓝牙进行设备控制。系统提供多级异常检测功能，当检测到烟雾火灾、环境异常或健康指标异常时，将通过本地灯光报警与蓝牙消息推送及时通知用户，实现全方位的智能家居守护。

## 2.3 器件选型

### 2.3.1 主控制器（STM32H753ZIT6）

![STM32H7核心板实物图](picture/2-2.jpg)

**选型依据：** 鉴于系统需运行轻量级卷积神经网络（GestureNet）并同时调度FreeRTOS多任务（图像接收、传感器融合、云端通信），系统对主控芯片的算力和内存有极高要求，传统的F1/F4系列难以支撑。

    * **(1) 内核架构**

    * **(2) 存储资源**
        板载2MB Flash和1MB RAM，足以容纳AI模型权重（约432KB）及运行时的大容量图像缓冲区（64x64张量）。
    * **(3) 外设接口**
        具备丰富的高速UART和DMA通道，支持与OpenMV进行1.5Mbps的高速通信，确保数据传输不阻塞CPU。

### 2.3.4 传感器模块

**选型依据：** 根据“安防+健康”的双重需求，选取了各领域成熟度高、驱动适配性好的传感器组合。

1. **健康监测类**
    * **(1) MAX30102心率血氧传感器**
        集成红光/红外光LED，体积微小。通过I²C接口输出FIFO数据，配合算法可精确计算SpO2和心率，适合指尖佩戴测量。
2. **环境安防类**
    * **(2) MQ-2烟雾传感器**

# 3 系统硬件及软件设计

## 3.1 MQ-2气体传感器部分（李成基）

### 3.1.1 介绍
MQ-2气体传感器是一种常用的气体传感器，用于检测空气中的烟雾浓度。工作原理是基于半导体气敏元件的电阻变化。当烟雾气体进入传感器时，它会与气敏元件表面的敏感材料发生化学反应，导致电阻值发生变化。通过测量电阻值的变化，可以推断出烟雾浓度的大小。

![MQ-2气体传感器实体图](picture/3-1.jpg)
**图 3-1 MQ-2气体传感器实体图**

![MQ-2气体传感器原理图](picture/3-2.png)
**图 3-2 MQ-2气体传感器原理图**

**工作原理：** 使用MQ-2型烟雾传感器属于二氧化锡(SnO2)半导体气敏材料，属于表面离子式N型半导体。处于200~3000摄氏度时，二氧化锡表面吸附空气中的氧，形成氧的负离子吸附，使半导体中的电子密度减少，从面使其电阻值增加。当与烟雾接触时，如果晶粒间界处的势垒收到烟雾的调至面变化，就会引起表面导电率的变化。利用这一点就可以获得这种烟雾存在的信息。烟雾浓度越大导电率越大，输出电阻越低，则输出的模拟信号就越大。

### 3.1.2 开发过程
1. **MQ-2传感器驱动头文件（mq2.h）核心说明**
    * **(1) 文件定位与作用**
        mq2.h 作为 MQ-2 烟雾传感器的驱动配置头文件，是传感器硬件与上层应用程序的接口层。核心实现硬件参数抽象化配置与功能函数标准化声明，既保证驱动代码的可移植性，也降低上层代码对硬件底层的依赖。
    * **(2) 关键配置与设计逻辑**
        * **模式宏定义（MODE）：** 通过 `define MODE 1` 实现传感器工作模式的一键切换（1为模拟AO模式，0为数字DO模式）。模拟模式下采集连续的浓度电压信号，数字模式下仅输出“超标/正常”的电平信号，适配不同精度需求的应用场景。
        * **硬件引脚宏定义：** 基于 MODE 的配置，分别定义模拟 AO 引脚（PA0，ADC通道0）、数字 DO 引脚（PA1）的时钟、端口、引脚号。所有硬件参数集中管理，修改时仅需调整宏定义，无需改动驱动实现代码，符合嵌入式开发“硬件与逻辑解耦”的设计原则。
        * **采集稳定性配置：** `define MQ2_READ_TIMES 10` 定义 ADC 采集次数，通过多次采集取平均的方式过滤模拟信号噪声，提升数据可靠性。
        * **函数接口声明：** 声明 `MQ2_Init()`（硬件初始化）、`MQ2_GetData()`（原始数据读取）、`MQ2_GetData_PPM()`（浓度值换算）3个核心函数，为上层代码提供标准化调用接口，隐藏底层硬件操作细节。
        * **头文件保护机制：** 通过 `ifndef __MQ2_H` 等指令防止头文件重复包含，避免编译阶段的变量/函数重复定义错误，符合 C 语言工程化开发规范。

2. **MQ-2传感器驱动实现文件（mq2.c）核心说明**
    * **(1) 文件定位与作用**
        mq2.c 是 mq2.h 声明接口的具体实现文件，基于 STM32F103ZE 芯片的硬件特性，完成传感器初始化、数据采集、浓度换算的底层逻辑封装，是传感器功能落地的核心载体。
    * **(2) 核心函数实现逻辑**
        * **MQ2_Init()：** 根据 `mq2.h` 的 MODE 配置分模式初始化硬件。
            * **模拟模式：** 将 AO 引脚配置为模拟输入模式，使能 ADC 时钟并完成 ADC 初始化与校准，保证模拟电压信号的有效采集。
            * **数字模式：** 将 DO 引脚配置为上拉输入模式，实现传感器数字电平信号的检测。
        * **MQ2_GetData()：** 核心数据读取函数，兼顾稳定性与场景适配。
            * **模拟模式：** 按 `mq2.h` 定义的采集次数（10次）循环读取 ADC 值，累加后取平均值，过滤模拟信号的随机噪声，返回 12 位 ADC 原始值（0~4095）。
            * **数字模式：** 读取 DO 引脚电平，通过电平取反转换为“0（正常）/1（超标）”的状态值，直观反映烟雾是否超标。
        * **MQ2_GetData_PPM()：** 仅模拟模式生效。基于 MQ-2 传感器的电压-浓度特性曲线，将 ADC 原始值转换为电压值，再通过传感器电阻（Rs）与洁净空气电阻（R0）的比值，拟合计算出烟雾浓度的 PPM（每百万分之一）值，实现从“原始电信号”到“直观浓度值”的转换，满足量化分析需求。

## 3.2 HC-05蓝牙部分（李成基）

### 3.2.1 介绍
HC-05是一款功能强大的经典蓝牙模块，由爱信电子（EGBT）生产。
它基于蓝牙2.0标准，支持多种传输协议，包括串口通信（UART）和蓝牙SPP（串口通信）。
HC-05可以在主设备模式（Master）或从设备模式（Slave）之间切换，具有较高的灵活性。
它支持蓝牙连接密码的设置，以提高安全性。
HC-05具有6个引脚，包括VCC（供电）、GND（接地）、TXD（发送数据）、RXD（接收数据）、STATE（状态）和EN（使能）。
STATE引脚可用于检测连接状态和模块工作模式。
HC-05可以通过AT指令进行配置和控制，例如更改蓝牙名称、波特率、配对密码等

### 3.2.2 开发过程
1. **连接硬件**
    * **(1) 电源连接**
        将 HC-05 模块的 `VCC` 引脚连接到 STM32 的 5V 电源引脚，`GND` 引脚连接到 STM32 的地引脚。
    * **(2) 串口通信连接**
        将 HC-05 模块的 `TXD` 引脚连接到 STM32 的 UART 接收引脚（例如 `USART1_RX`），`RXD` 引脚连接到 STM32 的 UART 发送引脚（例如 `USART1_TX`）。
    * **(3) AT 模式控制（可选）**
        如果需要进行模块的配置或进入 AT 命令模式，可以将 HC-05 模块的 `EN` 引脚连接到 STM32 的一个 GPIO 引脚，并在代码中控制该引脚的状态。
2. **STM32 串口底层配置（标准库）**
    * **(1) 时钟使能配置**
        通过标准库函数开启 USART1 及对应 GPIO 端口的时钟。
        * **时钟开启：** 开启总线的 USART1 时钟；使能 GPIOA 和 GPIOB 时钟，适配 PA9/PA10 引脚。
    * **(2) GPIO 引脚模式配置**
        将 PA9（TX）配置为“推挽复用输出模式”，PA10（RX）配置为“浮空输入模式”。
        * **PA9 配置：** 初始化 `GPIO_InitTypeDef` 结构体，设置 PA9 的模式为 `GPIO_Mode_AF_PP`（复用推挽输出），速度为 50MHz。
        * **PA10 配置：** 设置 PA10 的模式为 `GPIO_Mode_IN_FLOATING`（浮空输入），匹配串口接收的电平检测需求。
    * **(3) 串口核心参数配置**
        初始化 `USART_InitTypeDef` 结构体，严格匹配 HC-05 的通信参数。
        * **参数设置：** 波特率 `USART_BaudRate_9600`；数据位 `USART_WordLength_8b`；停止位 `USART_StopBits_1`；校验位 `USART_Parity_No`；模式 `USART_Mode_Tx | USART_Mode_Rx`（同时启用发送和接收）；流控 `USART_HardwareFlowControl_None`（无硬件流控）。
        * **参数写入：** 调用 `USART_Init(USART1, &USART_InitStructure)` 完成参数写入。
    * **(4) 串口中断配置**
        为实现数据的实时收发，配置 USART1 的中断控制器（NVIC）。
        * **全局中断：** 使能 USART1 的全局中断 `NVIC_EnableIRQ(USART1_IRQn)`。
        * **优先级配置：** 配置中断优先级（抢占优先级、响应优先级），确保串口中断不被其他低优先级中断阻塞。
        * **接收中断：** 启用串口接收中断 `USART_ITConfig(USART1, USART_IT_RXNE, ENABLE)`，当接收寄存器非空时触发中断。
        * **发送中断（可选）：** 启用发送完成中断 `USART_ITConfig(USART1, USART_IT_TC, ENABLE)`，用于发送完成后的状态判断。
    * **(5) 串口使能**
        调用 `USART_Cmd(USART1, ENABLE)` 激活 USART1，完成底层硬件配置。
3. **HC-05 通信功能开发**
    * **(1) 数据发送功能实现**
        基于标准库封装串口发送函数，支持单字节、字节数组、字符串发送。
        * **单字节发送：** 通过 `USART_SendData(USART1, data)` 发送单个字节，循环等待发送寄存器为空 `USART_GetFlagStatus(USART1, USART_FLAG_TXE)`，确保数据发送完成。
        * **字符串/数组发送：** 遍历待发送数据，逐字节调用单字节发送函数，适配 HC-05 的 AT 指令、自定义数据的发送需求（如发送 `AT+NAME=BLUETOOTH` 修改模块名称）。
    * **(2) 数据接收功能实现**
        通过中断服务函数实现异步接收，避免 CPU 轮询占用资源。
        * **中断服务函数：** 编写 `USART1_IRQHandler()`，当检测到“接收寄存器非空”中断时，读取接收数据 `USART_ReceiveData(USART1)`。
        * **接收缓冲区：** 设计接收缓冲区（如数组 `USART1_Rx_Buf`），将接收的数据存入缓冲区，并记录接收长度。
        * **接收完成标志：** 定义接收完成标志位（如 `USART1_Rx_Flag`），当检测到结束符（如换行符 `\n`）或缓冲区满时，置位标志位，通知主程序处理数据。
    * **(3) HC-05 AT 指令交互开发**
        基于上述收发函数，编写 HC-05 的配置逻辑。
        * **AT 指令模式触发：** 若接有 KEY 引脚，通过 GPIO 置高电平，延时后发送 `AT` 测试指令，验证模块是否进入 AT 模式（返回 `OK` 则成功）。
        * **常用指令封装：** 编写函数实现 HC-05 参数配置，如修改名称（`AT+NAME=XXX`）、修改波特率（`AT+UART=9600,8,1,0,0`）、查询配对码（`AT+PIN?`）等。
        * **指令响应解析：** 发送 AT 指令后，读取接收缓冲区的响应数据，解析 `OK`、`ERROR` 等关键字，判断指令执行结果。

## 3.3 GY30数字光强传感器检测与报警（李义旻）

### 3.3.1 介绍
![GY30数字光强传感器电路图](picture/3-3.png)
**图 3-3 GY30数字光强传感器电路图**

**原理：** GY30光强传感器基于BH1750芯片实现数字式光照检测，其核心原理是利用内置光敏二极管阵列感应环境光子的光电效应——当光线照射时，半导体材料激发产生与光强成正比的微安级电流，该电流经芯片内部I/V转换电路转为电压信号后，直接由16位高精度ADC进行模数转换并量化处理，最终通过I²C数字接口直接输出以勒克斯（lux）为单位的数字量，无需外接ADC或复杂校准电路，具备响应快、功耗低、抗干扰强的特点。

### 3.3.2 开发过程
1. **硬件连接**
    * **(1) 引脚配置**
        将STM32的GPIO引脚配置为开漏输出模式，连接GY-30模块的时钟线和数据线。
2. **IIC通信协议实现**
    * **(1) 信号时序生成**
        通过精确微秒级延时产生起始和停止信号，确保总线状态转换符合协议标准。
    * **(2) 双向数据传输**
        动态切换数据线方向（输出/输入），实现主机发送命令和接收从机应答。
    * **(3) 数据收发机制**
        按位传输数据位，读取时先获取高8位数据，再读取低8位并组合成16位整型值。
3. **传感器控制逻辑实现**
    * **(1) 初始化序列**
        依次发送上电命令、复位命令、测量模式配置命令。
    * **(2) 数据获取流程**
        发送读地址请求后，连续读取两个字节的光照强度数据。
4. **主循环处理**
    周期性获取16位原始数据，根据测量模式换算为实际光照强度值，通过串口输出验证结果
5. **对光强进行判断**
    当测得光强小于50lux时，代表烟雾浓度过高，蜂鸣器发出警报，LED灯常亮，当测得光强大于50lux时，蜂鸣器和LED关闭

## 3.4 HC-SR04超声波传感器检测（李义旻）

### 3.4.1 介绍
![HC-SR04超声波传感器电路图](picture/3-4.png)
**图 3-4 HC-SR04超声波传感器电路图**

**原理：** HC-SR04超声波测距模块通过发射和接收超声波来测量距离：主控器向Trig引脚发送至少10μs的高电平触发信号后，模块自动发射8个40kHz的超声波脉冲并启动计时；超声波遇到障碍物反射回来被接收器捕获，此时Echo引脚输出高电平，其持续时间即为超声波往返时间；最后通过公式"距离=(高电平时间×声速)/2"计算得出障碍物距离，其中声速通常取340m/s。

### 3.4.2 开发过程
1. **硬件初始化**
    * **(1) 触发引脚**
        配置为推挽输出模式，初始状态拉低。
    * **(2) 回波引脚**
        配置为浮空输入模式，避免外部电路干扰。
    * **(3) 定时器**
        配置为1MHz计数频率（每微秒计数1次）。
2. **测距流程**
    * **(1) 发送触发**
        控制触发引脚输出20微秒高电平脉冲，随后拉低。
    * **(2) 等待响应**
        轮询检测回波引脚电平，直到其变为高电平。
    * **(3) 启动计时**
        在回波引脚变高的瞬间清零定时器计数器，开始计时。
    * **(4) 等待结束**
        持续检测回波引脚，直到其变为低电平。
    * **(5) 读取时差**
        记录定时器的计数值，即为超声波往返所消耗的微秒数。
3. **计算距离**
    将测得的时间差除以58，结果单位为厘米。
4. **判断是否有人**
    当测得距离小于30cm时，在LCD屏幕上显示“PERSON”代表有人在，否则显示“NOBODY”代表没有人。
5. **避免干扰**
    每次测量需间隔至少60毫秒再发起下一次触发，避免超声波余波干扰。

## 3.5 ESP8266 WiFi传感器检测（王定宇）

### 3.5.1 介绍

**图 3-5 WiFi传感器电路图**

ESP8266支持三种天线接口形式：板载PCB天线、IPEX接口和邮票孔接口，板载PCB天线和IPEX接口天线客户可直接使用，无需添加任何匹配电路。如果客户需要在大板上设计天线部分，可使用ESP8266邮票孔天线接口，这种设计时大板需要预留匹配电路，如下：

![WiFi射频参考电路图](picture/3-6.jpg)
**图 3-6 WiFi射频参考电路图**

ESP8266-01 是集成 WiFi 的 SoC（System on Chip），核心是 Tensilica L106 32 位 MCU（时钟 80MHz，可达 160MHz），支持低功耗 RISC 架构。
模块上电后（CH_PD 高），MCU 从 SPI 闪存加载固件。使用 AT 命令或自定义代码处理 WiFi 连接、数据传输。接收 HTTP 请求后通过 UART/GPIO 处理。

### 3.5.2 开发过程
![WiFi传感器工作流程图](picture/3-7.png)
**图 3-7 WiFi传感器工作流程图**

1. **硬件上电与初始化**
    将 ESP8266 模块与主控（如 STM32）通过串口（TX/RX）连接后，给模块上电，进入 “上电等待” 阶段：等待模块完成硬件初始化（约 2~3 秒，指示灯会出现闪烁），确保模块进入可通信状态。
2. **AT 指令通信验证**
    通过主控向 ESP8266 发送 “AT” 测试指令 ：
    * 若模块返回 “OK”，说明串口通信链路（波特率、接线）正常；
    * 若未返回 “OK”，则执行 “检查接线 / 电源 / 波特率”，直到通信正常。
3. **关闭回显配置**
    向模块发送 “ATE0” 指令 ：关闭 AT 指令的回显功能（避免模块重复返回输入的指令内容），减少通信冗余数据，保证后续指令交互的简洁性。
4. **设置 Wi-Fi 工作模式**
    发送 “AT+CWMODE=1” 指令 ：将 ESP8266 配置为 “Station 模式（从机模式）”，即模块作为 Wi-Fi 客户端，可连接外部路由器网络（适配 “接入局域网” 的场景）。
5. **连接目标 Wi-Fi 网络**
    发送 “AT+CWJAP="SSID","密码"” 指令 （需替换为实际路由器的 SSID 和密码）：
    * 若模块返回“WIFI CONNECTED”，说明 Wi-Fi 连接成功；
    * 若未成功，需检查 SSID / 密码正确性、路由器信号强度，重新执行该指令直到连接成功。
6. **配置单连接模式**
    发送“AT+CIPMUX=0”指令 ：将 ESP8266 设置为 “单连接模式”，即模块同一时间仅与一个服务器建立网络连接（适配多数物联网场景的单设备通信需求）。
7. **进入主功能循环**
    完成上述配置后，ESP8266 进入“主循环”阶段：可基于此实现具体功能（如与云平台建立 TCP/UDP 连接、上传传感器数据、接收远程控制指令等），完成 Wi-Fi 模块的业务部署。

## 3.6 物联网设备管理平台（王定宇）

### 3.6.1 介绍
物联网平台在该智能家居系统中承担 “**数据中枢 + 远程管控 + 服务支撑**” 的核心作用，具体作用可分为以下 4 个维度：

1. **设备接入与统一管理**

    * 统一存储设备的认证密钥、部署位置等信息，支持设备的批量配置、分组管理，降低多设备的运维复杂度。
2. **数据汇聚与存储**
    平台是智能家居系统的**数据中枢**：
    * 接收并存储设备上传的各类数据（如烟雾浓度、环境参数、设备状态等），解决本地存储容量有限的问题；
    * 提供数据持久化能力，支持历史数据的查询、回溯（如查看某时段的烟雾浓度变化），为后续分析提供数据基础。
3. **远程管控与交互**
    平台实现了 “用户 - 设备” 的跨空间交互：
    * 支持用户通过手机 APP / 网页端，远程查看设备状态（如图中 “设备详情”）、下发控制指令（如远程关闭电器、调整安防模式）；
    * 当设备触发异常（如烟雾浓度超标），平台可将告警信息推送至用户终端，实现 “本地 + 云端” 的双重告警，提升智能家居的安全性。
4. **扩展与智能化支撑**
    平台为系统的功能扩展提供基础：
    * 可对接第三方服务（如语音助手、云 AI 能力），实现更智能的场景联动（如 “检测到烟雾→自动关闭燃气阀 + 推送告警”）；
    * 基于平台的数据分析能力，可挖掘用户习惯（如日常作息对应的设备使用规律），实现智能家居的自适应调节。
    
    简言之，物联网平台让该智能家居系统从 “本地单机控制” 升级为 “云端化、远程化、智能化” 的综合服务系统，是连接设备、用户与服务的核心枢纽

### 3.6.2 开发过程
1. **云端服务器设置**
    * **(1) 产品与设备创建**
        登录 OneNET 平台，创建“智能家居-环境监测”品类产品，定义数据模型（物模型），添加测试设备并获取核心三元组（ProductKey、DeviceName、DeviceSecret）。
    * **(2) 通信 Topic 配置**
        配置双向通信 Topic：
        * **上行 Topic：** 用于设备向云端上传传感器数据。
        * **下行 Topic：** 用于云端向设备下发控制指令。
2. **使用 MQTTX 进行仿真测试**
    * **(1) 客户端连接**

    * **(1) 数据封装**
        按照平台要求的 JSON 数据格式（如 Alink 协议），封装包含烟雾浓度、温湿度等模拟数据的 Payload。
    * **(2) 上行推送**
        通过 MQTTX 向上行 Topic 发送数据，并登录云端控制台查看“设备详情”或“日志服务”，验证数据是否成功解析并实时刷新显示。

## 3.7 MAX30102心率血氧传感器（杨正）

### 3.7.1 介绍
MAX30102心率血氧传感器是一种集成了光学传感器和信号处理器的模块，广泛应用于心率监测、脉搏氧饱和度监测以及其他生物参数检测等医疗领域。它具有高度集成、低功耗、高精度等特点，能够实时检测心率和血氧饱和度。模块内部集成了红外LED、红色光LED和光电检测器，通过红外LED和红色光LED照射皮肤，然后光电检测器采集反射光信号，进而进行血氧饱和度和心率的计算。

![MAX30102心率血氧传感器实体图](picture/3-10.png)
**图 3-10 MAX30102心率血氧传感器实体图**

![MAX30102心率血氧传感器原理图](picture/3-11.png)
**图 3-11 MAX30102心率血氧传感器原理图**

光电容积法的基本原理是利用人体组织在血管搏动时造成透光率不同来进行脉搏和血氧饱和度测量的。光源一般采用对动脉血中氧合血红蛋白（Hb02）和血红蛋白（Hb）有选择性的特定波长的发光二极管（一般选用660nm附近的红光和900nm附近的红外光）。当光束透过人体外周血管，由于动脉搏动充血容积变化导致这束光的透过光率发生改变，此时由光电变换器接收人体组织反射的光线，转变为电信号并将其放大和输出。由于脉搏是随心脏的搏动而周期性变化的信号，动脉血管容积也周期性变化，因此光电变换器的电信号变化周期就是脉搏率。

### 3.7.2 开发过程
MAX30102 作为核心的心率 / 血氧检测传感器，以下是基于 STM3H753 系列芯片、标准库完成该传感器驱动开发的完整流程，覆盖硬件适配、底层驱动、功能实现全环节：

1. **硬件适配与前期准备**
    * **(1) 硬件连接规划**
        MAX30102 与 STM32F103 的物理连接遵循 I2C 通信规范 + 中断引脚适配原则，核心引脚连接如下：
        * **供电：** MAX30102 的 VDD 接 3.3V 电源、GND 与 STM32 共地，确保供电稳定（3.3V±0.1V）；
        * **I2C 通信：** SDA 引脚接 STM32 GPIOB9、SCL 引脚接 GPIOB8（代码中复用通用 I2C 驱动），引脚需外接 4.7KΩ 上拉电阻；
        * **中断引脚：** INT 引脚接 STM32 GPIOB4（代码中定义为 `MAX30102_INT_PIN`），配置为浮空输入模式（MAX30102 内部已上拉）；
        * **额外：** 传感器需贴紧皮肤安装，确保光学检测窗口无遮挡，避免环境光干扰。
    * **(2) 通信参数确认**
        MAX30102 默认 I2C 通信参数：
        * **设备地址：** 写地址0xAE（代码中 `I2C_WRITE_ADDR`）、读地址0xAF（代码中 `I2C_READ_ADDR`）；
        * **通信速率：** 标准 I2C 速率（100Kbps），匹配STM32 通用 I2C 驱动的速率配置；
        * **数据格式：** 寄存器为 8 位地址 + 8 位数据，FIFO 数据为 24 位（有效数据 20 位）。
2. **底层驱动开发**
    * **(1) 寄存器写函数（maxim_max30102_write_reg）**
        * 启动 I2C 通信 `IIC_Start()` ，发送设备写地址，等待应答；
        * 发送目标寄存器地址，等待应答；
        * 发送待写入的数据，等待应答；
        * 停止 I2C 通信 `IIC_Stop()` ；
        * 校验所有应答状态，无错误则返回 0，否则返回 - 1（通信失败）。
    * **(2) 寄存器读函数（maxim_max30102_read_reg）**
        * 启动 I2C 通信，发送设备写地址 + 目标寄存器地址（完成读地址指向）；
        * 重启 I2C 通信，发送设备读地址，等待应答；
        * 读取寄存器数据，无需发送应答 `IIC_Read_Byte(0)` ；
        * 停止 I2C 通信，校验应答状态，返回读取结果或错误码。
    * **(3) 传感器初始化配置**
        实现 `maxim_max30102_init()` 函数，完成 MAX30102 的工作参数配置。先初始化 INT 引脚，再依次配置核心寄存器：
        * **中断使能寄存器（REG_INTR_ENABLE_1/2）：** 开启关键中断（0xc0），关闭无用中断（0x00）；
        * **FIFO 寄存器（REG_FIFO_WR_PTR/OVF_COUNTER/RD_PTR）：** 重置 FIFO 读写指针、溢出计数器为 0；
        * **FIFO 配置寄存器（REG_FIFO_CONFIG）：** 设置采样平均次数为 1、FIFO 溢出循环、几乎满阈值 17；
        * **模式配置寄存器（REG_MODE_CONFIG）：** 设置为 SpO2 模式（0x03），同时启用红光、红外光 LED；
        * **SpO2 配置寄存器（REG_SPO2_CONFIG）：** 设置 ADC 量程 4096nA、采样率 100Hz、LED 脉冲宽度 400μs；
        * **LED 功率寄存器（REG_LED1/2_PA、REG_PILOT_PA）：** 配置红光 / 红外光 LED 功率为 7mA，PILOT LED 为 25mA；
        每一步寄存器写入后校验返回值，任意一步失败则返回 - 1，全部成功返回 0。
    * **(4) FIFO 数据读取**
        实现 `maxim_max30102_read_fifo()` 函数，读取心率 / 血氧的光学检测数据：
        * 先读取并清除中断状态寄存器，避免中断残留影响；
        * 通过 I2C 读取 FIFO 数据寄存器 `REG_FIFO_DATA`，连续读取 6 字节数据（红光 3 字节 + 红外光 3 字节）；
        * 将读取的字节拼接为 24 位数据，屏蔽高 4 位无效数据，保留低 20 位有效数据 `*pun_red_led&=0x03FFFF`；
        * 分别存储红光 `pun_red_led`、红外光 `pun_ir_led` 数据，返回通信状态（0 = 成功，-1 = 失败）。
    * **(5) 传感器复位功能**
        实现 `maxim_max30102_reset()` 函数：
        * 向模式配置寄存器 `REG_MODE_CONFIG` 写入复位指令（0x40）；
        * 校验写入结果，返回复位成功 / 失败状态。
3. **功能调试与验证**
    * **(1) 基础通信测试**
        调用 `maxim_max30102_reset()` 复位传感器，验证 I2C 通信是否正常；
        读取传感器 ID 寄存器（未在代码中显式实现，可扩展），确认设备存在；
        调用 `maxim_max30102_init()` 初始化传感器，检查返回值是否为 0，确认初始化成功。
    * **(2) 数据读取测试**
        循环调用 `maxim_max30102_read_fifo()`，读取红光、红外光原始数据；
        打印原始数据至串口，验证数据是否稳定（无固定 0 值、无乱码）；   
        对比不同佩戴状态（贴紧 / 远离皮肤）的数据变化，确认光学检测有效。
    * **(3) 异常处理验证**
        断开 SDA/SCL 引脚，测试读写函数是否返回 - 1（通信失败）；
        配置错误的 I2C 地址，验证应答校验机制是否生效；
        长时间读取数据，观察 FIFO 溢出是否被正确处理（溢出计数器重置）。

### 3.8.2 高可靠性通信协议设计
由于 64x64 灰度图像的单帧数据量高达 4096 字节，在 1.5Mbps 高速传输下极易受电磁干扰导致比特翻转或丢包。为确保数据完整性，设计了包含**帧同步、长度校验、数据校验**的自定义数据链路层协议。

**1. 协议帧格式定义**
数据包总长度为 4103 字节，具体结构如下表所示：

**表 3-1 图像传输协议帧结构**

| 字段 | 偏移量 | 长度 | 值 / 定义 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| **帧头** | 0 | 2 Byte | `0xAA`, `0x55` | 双字节异构帧头，防止数据中偶然出现的单字节误判 |
| **数据长度** | 2 | 2 Byte | `0x1000` (4096) | 有效载荷长度（大端模式），支持变长扩展 |
| **校验和** | 4 | 1 Byte | `Checksum` | 累加和校验（Sum & 0xFF），用于检测传输误码 |
| **图像数据** | 5 | 4096 Byte | `Pixel[0]...[4095]` | 64x64 像素灰度数据，按行扫描（Row-Major） |
| **帧尾** | 4101 | 2 Byte | `0x5A`, `0xA5` | 结束标识，用于辅助判断帧边界 |

**2. 校验算法逻辑**
校验和字段采用简单的**累加和（Checksum）**算法。发送端在发送前遍历 4096 个像素字节进行累加，结果对 256 取模得到 8 位校验值；接收端在接收完成后重复此计算，若计算值与接收到的校验位不一致，则判定为坏帧并直接丢弃，不进行后续 AI 推理，从而避免错误数据导致的误识别。

### 3.8.3 OpenMV端采集程序开发（Python）
OpenMV 端基于 MicroPython 框架开发，主要负责传感器配置、图像预处理及数据包发送，核心代码文件为 `get_camera.py`。

1. **传感器与显示初始化**
    * **(1) 传感器配置**
        初始化 OV5640 传感器，设置像素格式为 `GRAYSCALE`（灰度模式，1 字节/像素），分辨率设置为 `QQVGA2` (128x160) 以适配 LCD 显示比例。调用 `sensor.skip_frames(time=2000)` 等待自动增益和白平衡稳定。
    * **(2) 高速串口配置**
        初始化 UART3 接口，波特率设定为 **1500000 (1.5Mbps)**，并将 `timeout_char` 设置较小以避免发送阻塞。理论传输速度达 150KB/s，传输一帧 4KB 图像仅需约 27ms，满足 30FPS 的实时性要求。

2. **图像预处理与缩放**
    * **(1) 图像捕获**
        调用 `sensor.snapshot()` 获取原始图像，用于本地 LCD 实时显示，方便调试对焦。
    * **(2) 硬件缩放**
        使用 `img.copy()` 方法将原始图像硬件缩放为神经网络所需的 **64x64** 尺寸。该过程采用双线性插值算法，既保证了图像质量，又直接生成了符合 AI 模型输入层要求的张量数据。

3. **数据包组装与发送**
    * **(1) 数据打包**
        编写 `send_image_packet` 函数，首先计算图像数据的校验和，然后使用 `bytearray` 按照协议格式（帧头+长度+校验+数据+帧尾）一次性组装完整数据包。
    * **(2) 原子发送**
        调用 `uart.write(packet)` 将 4103 字节的数据一次性写入 UART 发送缓冲区，避免分段发送导致字节间隙过大，从而触发接收端的空闲中断误判。

### 3.8.4 STM32端接收驱动开发（C语言）
STM32 端采用 **HAL 库 + FreeRTOS** 架构，利用 **DMA（直接存储器访问）** 和 **UART 空闲中断** 技术，实现了零 CPU 占用的图像数据接收。

1. **底层硬件配置**
    * **(1) UART配置**
        USART3 配置为异步模式，波特率严格匹配 **1.5Mbps**，8 位数据位，1 位停止位，无校验位，并开启全局中断。
    * **(2) DMA配置**
        开启 USART3_RX 的 DMA 通道，配置为 **Circular（循环）模式**。循环模式允许 DMA 在缓冲区填满后自动回到起始地址继续传输，形成“环形缓冲区”，防止高速数据流中断。

2. **DMA双缓冲机制**
    * **(1) 缓冲区设计**
        在 `openmv_rx_task.c` 中定义了 **8206 字节**（2 倍数据包大小）的接收缓冲区 `dma_buffer`：
        `#define DMA_BUFFER_SIZE (OPENMV_PACKET_SIZE * 2)`
    * **(2) 运行原理**
        双倍缓冲区结合 DMA 循环模式，使得 STM32 可以在 CPU 处理前半部分数据（Ping）的同时，DMA 继续接收后半部分数据（Pong）。这种机制彻底消除了数据接收的“盲区”，有效防止了 1.5Mbps 高速传输下的数据溢出（Overrun Error）。

3. **空闲中断回调逻辑**
    利用串口空闲中断（IDLE Line Interrupt）检测数据帧的结束。当一帧 4103 字节的数据传输完成，总线进入空闲状态时，自动触发中断执行以下逻辑：
    * **(1) 停止DMA与计算长度**
        调用 `HAL_UART_DMAStop` 暂停接收，通过 `__HAL_DMA_GET_COUNTER` 计算当前接收到的有效数据长度。
    * **(2) 解析与重启**
        调用 `parse_receive_buffer` 解析缓冲区数据，随后立即调用 `HAL_UART_Receive_DMA` 重启接收，准备下一帧数据。该机制确保了 CPU 仅在每帧结束时介入，极大降低了系统负载。

### 3.8.5 图像解析与任务同步
在 FreeRTOS 任务层，设计了专门的 `AppTask_openmv_rx` 任务负责协议解析与数据分发。

1. **协议解析流程**
    * **(1) 帧头定位**
        遍历接收缓冲区，查找 `0xAA 0x55` 帧头位置。
    * **(2) 完整性检查**
        确认剩余数据量是否满足 4103 字节，并提取数据长度字段验证是否为 4096。
    * **(3) 校验与验证**
        提取图像数据计算累加和，与接收到的校验位比对；同时检查帧尾是否为 `0x5A 0xA5`。只有所有验证通过，才认定该帧为有效图像。

2. **任务间通信与同步**
    * **(1) 消息队列发送**
        解析成功的 64x64 图像数据被封装为 `ImageMsg_t` 结构体，通过 `osMessageQueuePut` 发送至 `imageQueue`。消息队列实现了内存隔离，防止数据在推理过程中被 DMA 覆写。
    * **(2) 信号量触发**
        调用 `osSemaphoreRelease(frameReadySem)` 释放信号量，唤醒高优先级的 AI 推理任务 (`InferenceTask`)，实现“采集完成即刻推理”的事件驱动机制。

3. **稳定性与性能监控**
    * **(1) 超时重连**
        任务维护 `last_rx_time` 时间戳，若超过 2000ms 未收到有效数据（如 OpenMV 断连），将强制复位 DMA 和串口，防止死锁。
    * **(2) FPS统计**
        任务每秒统计一次成功接收的帧数，通过 `rx_stats.fps` 变量实时反馈。实测在 1.5Mbps 波特率下，STM32 端接收帧率稳定在 **28~32 FPS**，满足实时手势识别需求。

1. **网络结构详解**

2. **设计原理**
    * **(1) 深度可分离卷积**

    * **(2) ReLU6 激活函数**
        对量化更友好，数值稳定性更好。
    * **(3) 全局平均池化**
        替代全连接层，减少参数，对空间位置具有鲁棒性。
    * **(4) Dropout 正则化**
        防止过拟合，提升泛化能力。

### 3.9.3 上位机Python工具链开发
为实现从数据采集到模型部署的高效流转，本项目开发了一套基于 Python 的完整上位机工具链，涵盖数据处理、清洗、训练、转换及验证六大环节。

1. **数据集采集工具 (collect_training_data.py)**
    * **(1) 串口通信与握手协议**
        基于 `pyserial` 开发，上位机与 STM32 采用 **921600** 高波特率通信以满足图像传输带宽。设计了可靠的“请求 - 响应”握手协议：
        * **请求：** PC 端发送 ASCII 指令 `CMD:GET_IMAGE`。
        * **响应：** STM32 收到指令后暂停 AI 推理任务，通过 UART1 透传 OpenMV 采集的 4096 字节 Raw 灰度数据。
        * **同步：** 引入超时重发机制（Timeout=200ms），防止因串口丢包导致的程序卡死。
    * **(2) 数据流解包与重组**
        * **帧校验：** 上位机接收数据后，首先校验帧头 (`0xAA 0x55`) 和帧尾 (`0x5A 0xA5`)，并计算累加和 (Checksum) 验证数据完整性。
        * **图像重构：** 将有效的 4096 字节 Payload 转换为 `numpy` 数组，并 reshape 为 `(64, 64)` 矩阵，最终通过 `PIL` 库生成 PNG 格式图像。
    * **(3) 自动化工作流与质量控制**
        * **智能存图：** 支持连续采集模式，自动根据当前设定的 `class_id`（如 0）创建标准目录结构（如 `dataset/raw/0_fist/`）。
        * **断点续传：** 启动时自动扫描目标文件夹中已存在的最大文件名索引（如 `img_0150.png`），从下一索引开始计数，完全避免历史数据覆盖。
        * **实时质量监测：** 使用 `OpenCV` 实时渲染预览窗口，并计算图像像素均值。若均值 **<30 (过暗)** 或 **>220 (过曝)**，系统将自动丢弃该帧并触发蜂鸣报警，从源头剔除劣质数据。

2. **数据增强工具 (augment_dataset.py)**
    * **(1) 增强流水线**
        利用 `torchvision.transforms` 构建离线增强流水线，将原始数据集扩充 5-10 倍，解决小样本过拟合问题。
        * **几何变换：** 随机旋转 (±40°)、平移 (±15%)、缩放 (0.85-1.15倍)、剪切 (±10°)。
        * **环境模拟：** 随机调整亮度 (±30%) 和对比度 (±30%)，模拟不同光照环境下的手势特征。
    * **(2) 遮挡鲁棒性优化**
        引入 **随机擦除 (Random Erasing)** 技术，以 30% 的概率随机遮挡图像中 2%-15% 的矩形区域。该策略有效模拟了手指被部分遮挡或手势不完整的真实场景，显著提升了模型在复杂环境下的抗干扰能力。

3. **模型训练框架 (train_model.py)**
    * **(1) 训练环境配置**
        基于 **PyTorch** 框架搭建，自动检测并启用 CUDA 加速。
        * **超参数：** 优化器选用 Adam (LR=0.001)，损失函数为 CrossEntropyLoss，批量大小 (Batch Size) 设为 32。
    * **(2) 动态训练策略**
        * **学习率衰减：** 使用 `ReduceLROnPlateau` 调度器，实时监测验证集 Loss，当连续 5 个 Epoch 不下降时自动减半学习率。
        * **早停机制 (Early Stopping)：** 若验证集准确率连续 15 个 Epoch 未提升，则判定模型收敛并提前终止训练，自动保存最佳权重 (`best_model.pth`)。
    * **(3) 产物输出**
        训练结束后，自动生成训练过程的 Loss/Accuracy 曲线图，并计算测试集上的 **混淆矩阵 (Confusion Matrix)**，精确评估模型对每一类手势（如拳头、手掌）的召回率与精确率。

4. **模型转换与算子优化 (convert_to_onnx_v2.py)**
    * **(1) 格式转换**
        将 `.pth` 权重导出为标准 **ONNX** 格式 (Opset Version 11)。脚本会自动验证输入输出张量形状 (`[1, 1, 64, 64]` → `[1, 5]`) 是否符合预期。
    * **(2) 图优化 (Graph Optimization)**
        调用 `onnx-simplifier` 库对计算图进行瘦身：
        * **常量折叠 (Constant Folding)：** 预计算静态节点的输出。
        * **算子融合：** 移除训练专用的 Dropout 层和无用的 Identity 节点，精简模型结构以符合 STM32 X-CUBE-AI 的导入要求。

5. **双端实时对比验证工具 (realtime_inference_compare.py)**
    * **(1) 闭环验证系统**
        开发了一个“PC - STM32”闭环验证工具，用于评估量化误差。
        * **流程：** PC 端随机下发一张测试图片给 STM32 → STM32 进行 INT8 推理并回传结果 → PC 端同时使用 Float32 模型进行推理。
    * **(2) 一致性分析**
        逐帧对比 PC 端（浮点精度）与 STM32 端（量化精度）的置信度差异。实验表明，在 1000 帧随机测试中，两者的分类结果一致率达 **90.5%**，平均置信度误差 **< 2%**，证明量化部署未造成明显的精度损失。

### 3.9.5 STM32 推理实现
STM32 端的推理系统基于 FreeRTOS 任务架构设计，通过事件驱动的方式高效协调图像接收、AI 计算与外设控制，核心流程包含任务调度、预处理优化、滤波算法与执行器映射四个环节。

1. **推理任务流程 (inference_task.c)**
    * **(1) 任务调度逻辑**
        推理任务 `AppTask_inference` 设置为高优先级（Priority 3），通过二值信号量 `frameReadySem` 与图像采集任务同步，实现“零轮询”的高效触发。
        * **挂起等待：** 任务平时处于阻塞状态，等待 CameraTask 释放信号量。
        * **数据获取：** 唤醒后从 `imageQueue` 消息队列中取出 4096 字节的原始图像数据，实现了采集与推理的内存解耦。
    * **(2) 核心处理代码**
        ```c
        void AppTask_inference(void *argument) {
            for(;;) {
                // 1. 等待图像就绪信号量 (超时1000ms)
                if(osSemaphoreAcquire(frameReadySem, 1000) == osOK) {
                    ImageMsg_t img_msg;
                    // 2. 从队列获取图像数据 (零拷贝)
                    if(osMessageQueueGet(imageQueue, &img_msg, NULL, 0) == osOK) {
                        uint8_t gesture_id;
                        float confidence;

                        // 3. 执行 AI 推理 (包含预处理、推理、后处理)
                        // 返回 0 表示推理成功，confidence 为置信度
                        uint8_t ret = InferenceTask_Run(img_msg.data, &gesture_id, &confidence);

                        if(ret == 0) {
                            // 4. OLED 显示识别结果
                            OLED_ShowGestureResult(gesture_id, confidence);

                            // 5. 执行手势控制逻辑 (滤波 + PWM控制)
                            GestureControl_HandleGesture(gesture_id, confidence);

                            // 6. 串口上报结果 (用于上位机波形显示)
                            UartTxTask_SendResult(gesture_id, confidence);
                        }
                    }
                }
            }
        }
        ```

2. **AI 核心处理与数值优化 (app_x-cube-ai.c)**
    * **(1) 图像预处理 (Pre-processing)**
        为了匹配 PyTorch 训练时的输入分布，STM32 端需对 `uint8` 图像进行标准化处理。
        * **归一化公式：** `pixel_float = (pixel_uint8 / 255.0 - 0.5) / 0.5`
        * **效果：** 将像素值从 `[0, 255]` 映射到 `[-1, 1]` 区间，提升模型收敛速度和推理精度。
    * **(2) Softmax 数值稳定性优化**
        模型输出的是 Logits（未归一化分数），需通过 Softmax 函数转换为概率。为防止指数运算溢出，采用了 **Shifted Softmax** 策略：
        * **最大值偏移：** 先找出 Logits 中的最大值 `max_val`。
        * **指数运算：** 计算 `exp(x - max_val)`，确保指数项始终 ≤ 0，避免 float 溢出。
        * **概率归一化：** `probability[i] = exp_val[i] / sum(exp_val)`。

3. **手势滤波算法 (gesture_control.c)**
    * **(1) 滑动窗口滤波**
        为消除手势切换过程中的识别抖动（如“布”变“拳”中间的过渡帧），设计了长度为 5 的环形缓冲区 `gestureBuffer`。
        * **统计机制：** 每次新识别结果入队，移除最旧结果，统计窗口内各手势 ID 的出现次数。
        * **决策阈值：** 仅当某种手势在窗口内出现次数 `≥ 3`（即占 60%）时，才判定为有效稳定手势，否则维持上一状态或输出 `NONE`。
    * **(2) 代码实现**
        ```c
        static uint8_t GestureFilter(uint8_t gesture_id) {
            // 更新滑动窗口缓冲区 (size=5)
            gestureBuffer[bufferIndex] = gesture_id;
            bufferIndex = (bufferIndex + 1) % GESTURE_FILTER_SIZE; // 环形指针

            // 统计众数
            for (int i = 0; i < 5; i++) {
                if (counts[i] > maxCount) {
                    maxCount = counts[i];
                    mostFrequent = i;
                }
            }

            // 阈值判断 (GESTURE_STABLE_COUNT = 3)
            if (maxCount >= GESTURE_STABLE_COUNT) {
                return mostFrequent;  // 输出稳定手势
            } else {
                return GESTURE_NONE;  // 不稳定
            }
        }
        ```

4. **手势映射与执行器控制**
    * **(1) 动作映射表**
        系统支持两种控制模式：**占空比调节** 和 **目标切换**。

        | 手势 ID | 手势名称 | 功能定义 | 控制逻辑 |
        | :--- | :--- | :--- | :--- |
        | **0** | Fist (拳头) | 关闭设备 | 设置 PWM 占空比为 0% |
        | **1** | Palm (手掌) | 高档运行 | 设置 PWM 占空比为 30% |
        | **2** | V-Sign (剪刀) | 低档运行 | 设置 PWM 占空比为 10% |
        | **3** | OK | 切换目标 | 在 LED 灯与蜂鸣器之间切换控制权 |

    * **(2) OK 手势防抖逻辑**
        针对“OK”手势的切换功能，增加了**状态锁机制** (`okGestureProcessed`)：当检测到 OK 手势时，仅触发一次切换动作，直到手势消失或变为其他手势后才释放锁，防止一次手势触发多次切换。
    * **(3) 软件 PWM 实现**
        利用 TIM2 定时器产生 1kHz 中断，在中断回调中通过计数器模拟 PWM 波形，独立控制 LED3 和蜂鸣器的亮度/音量。
        ```c
        void GestureControl_PWM_Update(void) { // 1ms 调用一次
            pwm_counter++;
            if (pwm_counter >= 100) pwm_counter = 0; // 100ms 周期

            // 独立控制 LED 和 蜂鸣器
            if (pwm_counter < led_duty)  HAL_GPIO_WritePin(GPIOB, GPIO_PIN_14, SET);
            else                         HAL_GPIO_WritePin(GPIOB, GPIO_PIN_14, RESET);

            if (pwm_counter < buzz_duty) HAL_GPIO_WritePin(GPIOG, GPIO_PIN_6, SET); // 蜂鸣器低电平触发需反相
            else                         HAL_GPIO_WritePin(GPIOG, GPIO_PIN_6, RESET);
        }
        ```

## 3.10 FreeRTOS实时操作系统任务架构

### 3.10.1 系统架构介绍
本项目采用 **FreeRTOS 实时操作系统** 进行多任务调度，实现了图像采集、AI 推理、传感器监测、数据通信等功能的并发执行。系统共包含 **7 个任务**，通过消息队列和信号量实现任务间通信与同步，确保实时性和系统稳定性。

### 3.10.3 各任务详细说明

1. **CameraTask - 图像采集任务**
    * **(1) 任务配置**
        * **任务文件：** `App/openmv_rx_task.c`
        * **优先级：** 3 (高优先级)
        * **触发周期：** 事件驱动（UART3 空闲中断）
    * **(2) 功能描述**
        通过 UART3 接收 OpenMV Cam 发送的 64x64 灰度图像。
        * **通信参数：** 波特率 1500000 bps，采用 DMA 循环接收。
        * **协议解析：** 校验帧头 `$IMG,4096`、帧尾 `\r\n` 及数据完整性。
        * **数据转发：** 将图像数据放入 `imageQueue` 消息队列（深度 5）。
        * **性能统计：** 实时计算图像接收帧率（FPS）。
    * **(3) 关键代码逻辑**
        ```c
        void AppTask_openmv_rx(void *argument) {
            for(;;) {
                // 1. UART3 DMA空闲中断触发
                // 2. 解析帧头 "$IMG,4096"
                // 3. 提取4096字节图像数据
                // 4. 校验帧尾 "\r\n"
                // 5. 放入imageQueue队列
                osMessageQueuePut(imageQueue, &img_msg, 0, 0);
                // 6. 发送信号量通知InferenceTask
                osSemaphoreRelease(frameReadySem);
            }
        }
        ```

2. **InferenceTask - AI 推理任务**
    * **(1) 任务配置**
        * **任务文件：** `App/inference_task.c`
        * **优先级：** 3 (高优先级)
        * **触发周期：** 事件驱动（`frameReadySem` 信号量）
    * **(2) 功能描述**
        * **数据获取：** 等待图像数据就绪，从 `imageQueue` 获取图像。
        * **AI 推理：** 调用 X-CUBE-AI 进行 GestureNet CNN 推理。
        * **预处理：** `uint8[4096]` → `float[4096]`，归一化到 `[-1, 1]`。
        * **后处理：** Softmax + argmax，得到手势 ID 和置信度。
        * **设备控制：** 滑动窗口滤波（size=5）防抖，调用 `GestureControl_HandleGesture()` 控制 LED/蜂鸣器。
        * **结果输出：** OLED 显示、UART1 上传、结果队列。
    * **(3) 关键代码逻辑**
        ```c
        void AppTask_inference(void *argument) {
            for(;;) {
                // 1. 等待图像就绪信号量
                osSemaphoreAcquire(frameReadySem, 1000);

                // 2. 从队列获取图像
                osMessageQueueGet(imageQueue, &img_msg, NULL, 0);

                // 3. 运行AI推理
                InferenceTask_Run(img_msg.data, &gesture_id, &confidence);

                // 4. OLED显示结果
                OLED_ShowGestureResult(gesture_id, confidence);

                // 5. 手势控制设备
                GestureControl_HandleGesture(gesture_id, confidence);

                // 6. 串口发送结果
                UartTxTask_SendResult(gesture_id, confidence);
            }
        }
        ```

3. **SensorTask - 传感器采集任务**
    * **(1) 任务配置**
        * **任务文件：** `App/sensor_task.c`
        * **优先级：** 2 (中优先级)
        * **触发周期：** 10ms（MAX30102 采样率 100Hz）
    * **(2) 多传感器采样策略**
        * **MAX30102 心率血氧：** 10ms 采样，1024 样本 FFT 算法计算。
        * **BH1750 光照强度：** 100ms 采样，I2C 读取 lux 值。
        * **HC-SR04 超声波：** 100ms 采样，距离测量（0-500cm）。
        * **MQ-2 烟雾传感器：** 100ms 采样，ADC 读取 PPM 浓度。
        * **DHT11 温湿度：** 2 秒采样，单总线协议读取。
        * **数据处理：** 移动平均滤波（窗口大小 3），调用 `GestureControl_CheckSensorAlarm()` 检查报警阈值。
    * **(3) 关键代码逻辑**
        ```c
        void AppTask_sensor(void *argument) {
            uint8_t other_sensor_counter = 0;
            uint8_t dht11_counter = 0;

            for(;;) {
                // MAX30102每10ms采集（100Hz，FFT需要）
                MAX30102_ReadFIFO(&redLED, &irLED);
                aun_red_buffer[buffer_index] = redLED;
                aun_ir_buffer[buffer_index] = irLED;
                buffer_index++;

                // 收集满1024样本后计算心率血氧
                if (buffer_index >= 1024) {
                    maxim_heart_rate_and_oxygen_saturation(
                        aun_ir_buffer, 1024, aun_red_buffer,
                        &spo2, &spo2_valid, &hr, &hr_valid);
                }

                // 其他传感器每100ms采集一次
                other_sensor_counter++;
                if (other_sensor_counter >= 10) {
                    BH1750_ReadData();     // 光照
                    HCSR04_GetDistance();  // 距离
                    MQ2_GetDataPPM();      // 烟雾

                    // DHT11每2秒读取一次
                    dht11_counter++;
                    if (dht11_counter >= 20) {
                        DHT11_Read(&dht11_data);
                    }
                }
                // 检查报警状态
                GestureControl_CheckSensorAlarm();
                osDelay(10);  // 10ms周期
            }
        }
        ```

4. **UartTxTask - 串口发送任务**
    * **(1) 任务配置**
        * **任务文件：** `App/uart_tx_task.c`

### 3.10.5 任务优先级设计原则
系统采用 **抢占式调度策略**，优先级设计遵循以下原则：

1. **实时性要求高的任务优先级高**
    * **(1) CameraTask（优先级 3）：** 图像数据接收不能丢帧。
    * **(2) InferenceTask（优先级 3）：** 手势识别需要实时响应。

2. **数据处理任务中等优先级**
    * **(1) SensorTask（优先级 2）：** 传感器采集周期性运行。
    * **(2) UartTxTask（优先级 2）：** 数据发送及时性要求中等。
    * **(3) UartRxTask（优先级 2）：** 命令接收及时处理。

3. **非关键任务低优先级**
    * **(1) OneNETTask（优先级 1）：** 云平台上传可容忍延迟。
    * **(2) DisplayTask（优先级 1）：** OLED 刷新 100ms 可接受。

### 3.10.6 性能优化策略

1. **堆栈大小配置**
    * **(1) InferenceTask (Task_inference)**
        * **配置值：** 16384 Bytes (4096 words)。
        * **依据：** AI 推理任务涉及深度神经网络（CNN）的矩阵运算及浮点处理，且需在栈上存储模型中间层的激活值（Activations），调用深度最大，因此分配最大的栈空间以防止溢出。
    * **(2) CameraTask (Task_openmv_rx) & UartTxTask**
        * **配置值：** 8192 Bytes (2048 words)。
        * **依据：** * **CameraTask：** 需处理 4096 字节的图像数据包解析与协议校验，局部缓冲区较大。
            * **UartTxTask：** 负责图像数据上传及长 JSON 字符串格式化（`sprintf`），发送缓冲区占用较高。
    * **(3) UartRxTask (Task_uart_rx)**
        * **配置值：** 4096 Bytes (1024 words)。
        * **依据：** 负责解析上位机指令及蓝牙数据，需预留足够空间应对突发长指令或连续数据包的处理。
    * **(4) SensorTask, DisplayTask & KeyProcTask**
        * **配置值：** 2048 Bytes (512 words)。
        * **依据：** * **SensorTask：** 涉及 MAX30102 心率血氧算法的浮点运算及多传感器数据融合。
            * **DisplayTask：** 涉及 OLED 显存刷新及 UI 绘图逻辑。
            * **KeyProcTask：** 处理按键的复杂逻辑判断与长按/连击检测。
    * **(5) KeyReadTask (Task_key_read)**
        * **配置值：** 1024 Bytes (256 words)。
        * **依据：** 该任务仅负责高频读取 GPIO 电平状态并更新按键状态机，无深度函数调用链，适中的堆栈即可满足中断上下文保存需求。
    * **(6) LedProcTask (Task_led_proc)**
        * **配置值：** 512 Bytes (128 words)。
        * **依据：** 该任务仅包含 GPIO 翻转与 `osDelay` 延时函数，无局部大数组变量，使用最小的堆栈空间即可维持 RTOS 任务切换所需的寄存器保存开销。

2. **CPU 占用率优化**
    * **(1) 事件驱动设计：** InferenceTask、UartTxTask 等任务采用信号量/队列阻塞，无数据时不占用 CPU。
    * **(2) 周期性休眠：** DisplayTask 每 100ms 运行一次，其余时间休眠让出 CPU。
    * **(3) DMA 传输：** UART3、UART1 采用 DMA 传输，减少 CPU 中断次数。
    * **(4) 软件 PWM 优化：** TIM2 定时器中断（1kHz）实现 PWM，占用率 < 1%。

3. **内存管理**
    * **(1) 静态分配：** 所有任务堆栈静态分配，避免动态内存碎片。
    * **(2) 缓冲区复用：** MAX30102 数据缓冲区采用滑动窗口，避免重复申请。
    * **(3) 全局数据共享：** `g_sensorData` 全局变量避免跨任务拷贝。

### 3.10.7 调试与监控
FreeRTOS 提供的任务监控功能：
1. **任务状态查看：** 通过 `vTaskList()` 查看所有任务状态（运行/就绪/阻塞/挂起）。
2. **CPU 占用率统计：** 通过 `vTaskGetRunTimeStats()` 查看各任务 CPU 占用。
3. **堆栈溢出检测：** 启用 `configCHECK_FOR_STACK_OVERFLOW` 检测栈溢出。
4. **断言调试：** `configASSERT()` 宏在调试阶段检查错误。

### 4.8.2 STM32端接收与解析流程
1. **UART3 硬件配置 (HAL库)**
    * **(1) 时钟与引脚初始化**
        使能 USART3 和 GPIOA 时钟，配置 PA11/PA12 为复用推挽输出模式 (AF7_USART3)。
    * **(2) 核心参数配置**
        配置 USART3 波特率为 1.5 Mbps，启用 DMA 接收模式，开启空闲中断 (`UART_IT_IDLE`) 以检测不定长数据帧结束。
    * **(3) DMA 双缓冲配置**
        设置 5000 字节的循环接收缓冲区 `uart3_rx_buffer`，启动 DMA 循环接收模式 (`HAL_UART_Receive_DMA`)。

2. **OpenMV 数据接收任务 (openmv_rx_task.c)**
    * **(1) 空闲中断处理**
        在 `USART3_IRQHandler` 中检测到空闲中断后，清除标志位，暂停 DMA，计算接收数据长度，并通过信号量 `uart3_rx_sem` 通知 CameraTask，随后立即重启 DMA。
    * **(2) 图像解析逻辑**
        CameraTask 等待信号量唤醒后，执行以下步骤：
        * **帧头定位：** 查找 `$IMG,4096` 标识符。
        * **长度校验：** 确认剩余数据长度是否满足 4098 字节。
        * **帧尾校验：** 验证最后两字节是否为 `\r\n`。
        * **数据提取：** 提取 4096 字节有效图像数据封装为 `ImageMsg_t`。
        * **消息转发：** 将图像消息放入 `imageQueue` 并释放 `frameReadySem` 触发 AI 推理。

3. **关键特性与优化**
    * **(1) 双缓冲机制**
        DMA 循环接收配合 FreeRTOS 队列转发，实现了接收与处理的异步解耦，有效防止高速数据流下的丢包。
    * **(2) 鲁棒性设计**
        包含超时重连机制（1秒无数据自动重置状态）和三重完整性校验（帧头/帧尾/长度），确保传输的每一帧图像数据有效可靠。
    * **(3) 性能监控**
        内置 FPS 统计逻辑，实时计算每秒成功接收的有效帧数，便于评估系统性能。

# 5 总结与展望

## 5.1 实训总结

本次实训以 “智能家居安防与健康守护” 为核心场景，基于 STM32 嵌入式平台，融合物联网、人工智能、多传感器融合等技术，完成了从需求分析、硬件选型、软件开发到系统联调的全流程开发，具体总结如下：

1. **实训核心成果**
    * **(1) 系统架构与功能落地**
        构建了 “硬件层 - 边缘计算层 - 云端层 - 应用层” 四层架构，实现核心功能闭环。
        * **硬件层：** 完成 OPENMV 摄像头、DHT11、BH1750、MQ-2、MAX30102、ESP8266、HC-05 等多模块适配，解决了 I2C/SPI 通信冲突及传感器干扰问题。
        * **边缘计算层：** 基于 STM32H7543ZIH6 实现 AI 手势识别、多传感器阈值判断及健康数据滤波，支持入侵置信度评分与参数掉电存储。
        * **云端层：** 利用OneNET MQTT 实现设备管理与数据上报，搭建可视化监控面板支持历史追溯。
        * **应用层：** 开发串口菜单、蓝牙近场控制、云端 APP 三种交互方式，覆盖多场景需求。
    * **(2) 关键技术突破**
        * **AI 边缘推理：** 打通 “PyTorch 训练 → ONNX 转换 → X-CUBE-AI 量化 → 部署” 流程，实现 5 种手势实时识别，准确率达 92%。
        * **健康算法：** 基于 MAX30102 采集 PPG 波形，经滑动平均滤波与峰值检测，心率误差 ≤±2 次/分，血氧误差 ≤±1%。
        * **通信适配：** 实现 Wi-Fi、蓝牙、串口的多协议适配与 “本地优先、云端兜底” 优先级管理策略。
    * **(3) 工程化能力提升**
        * **模块化思维：** 实现驱动层、算法层、应用层的解耦，提升代码可维护性。
        * **问题解决：** 攻克了 MAX30102 运动干扰、ESP8266 断连等实际工程难题。
        * **流程规范：** 形成了从需求拆解到系统联调的完整工程化开发流程。

2. **实训中暴露的问题**
    * **(1) 技术层面**
        * **AI 鲁棒性：** 强光/逆光下准确率降至 75%，且仅支持固定距离识别，缺乏自适应能力。
        * **数据延迟：** 多传感器采集存在约 200ms 同步延迟，云端控制平均延迟 500ms，实时性有待提升。
        * **算法深度：** 健康分析仅停留在基础计算，缺乏 HRV、睡眠监测等深度挖掘。
        * **兼容性：** 驱动代码耦合度较高，更换传感器型号（如 DHT22）需修改底层。
    * **(2) 工程层面**
        * **容错机制：** 缺乏硬件故障自检与通信断连后的本地降级策略。
        * **功耗管理：** 未进行低功耗设计，持续运行电流约 80mA，不适合电池供电。
        * **交互体验：** 交互方式单一，缺乏语音或触摸等便捷操作。

3. **实训经验沉淀**
    * **(1) 硬件先行原则**
        硬件选型时需充分考虑通信协议、供电需求、引脚兼容性，避免后期联调出现不可调和的硬件冲突。
    * **(2) AI 轻量化部署**
        针对嵌入式设备算力限制，优先选择参数量 <1M 的轻量级模型，结合 INT8 量化降低算力消耗。
    * **(3) 物联网降级策略**
        设计云端断连后的本地自治逻辑，确保核心功能（如本地安防告警）不受通信影响。
    * **(4) 数据时序同步**
        通过硬件定时器或软件时间戳实现数据同步采集，避免多源数据的时间偏差影响决策。

# 附录 C：用户操作简易指南

本系统支持**非接触式手势控制**与**远程蓝牙/云端控制**两种交互模式，具体操作说明如下：

### C.1 AI 手势控制说明
系统上电后默认进入手势识别模式，用户需将手掌置于摄像头前方 **15cm - 40cm** 范围内，系统识别成功后将在 OLED 屏显示结果并执行对应动作。

| 手势 ID | 手势名称 | 控制功能定义 |
| :---: | :--- | :--- |
| **0** | **Fist (拳头)** | **关闭设备**：将当前控制目标（LED或蜂鸣器）的 PWM 占空比设为 0% |
| **1** | **Palm (手掌)** | **高档运行**：将当前控制目标开启至 30% 强度（高亮/高音量） |
| **2** | **V-Sign (剪刀手)**| **低档运行**：将当前控制目标开启至 10% 强度（微亮/低音量） |
| **3** | **OK** | **切换目标**：在“LED 灯光”与“蜂鸣器”之间切换控制权。OLED 会提示 `Target: LED` 或 `Target: Buzz` |

### C.2 蓝牙控制说明

1. **APP 连接**：使用手机蓝牙助手搜索设备 `HC-05`，输入配对码 `1234`。
2. **指令列表**：
    * 发送字符 **`A`**：切换控制目标（等同于 OK 手势）。
    * 发送字符 **`B`**：一键关闭当前设备（等同于 Fist 手势）。
    * 接收数据：APP 端可实时接收系统推送的 `Temp: 25.3C, Smoke: 45 PPM` 等环境数据。
